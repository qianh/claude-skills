# PRD 需求拆分 + 技术方案生成

## 核心目标

将 PRD 文档拆分为可独立执行的开发任务，并**自动填充技术方案**——基于代码库的真实组件、Hook、工具函数使用数据，为每个任务推荐具体的实现方案。

### 与原有技能的关系

| 技能 | 定位 | 本技能如何整合 |
|------|------|----------------|
| `/prd-splitter` | 需求拆分，技术方案留空 | 完整继承需求拆分能力 |
| `/codebase-analyzer` | 代码库全量分析 | 按需触发，数据用于填充技术方案 |

### 核心价值

1. 开发拿到任务文档后**不需要再翻代码找组件**
2. 技术方案基于**项目真实使用数据**，不是凭空猜测
3. 新人也能快速上手，因为每个任务都附带了"项目里同类场景怎么做的"

---

## 触发条件

用户提供 PRD 文档（PDF、Word 等）并希望将其拆分为独立开发任务时使用。典型触发词：

- "拆分 PRD"、"分析 PRD"、"PRD 拆解"
- "把这个需求文档拆分一下"
- "帮我整理这个产品文档"
- "帮开发同学拆解这个需求"
- "拆分需求并生成技术方案"

```

## 阶段 A：代码库感知检查（必须首先执行）

### 步骤 A.1：检测代码库分析数据

按优先级检查以下路径：

```
检查顺序：
1. .ai-docs/DEV-GUIDE.md              — codebase-analyzer 的完整输出
2. .ai-docs/COMPONENT-SELECTOR.md     — 组件选择器
3. .ai-docs/_aggregated.json          — 汇总数据（最关键）
4. .ai-docs/_todo.txt                 — 是否有未完成的分析
```

### 步骤 A.2：根据检测结果决策

**情况 1：完整数据存在**（`_aggregated.json` + `DEV-GUIDE.md` + `COMPONENT-SELECTOR.md` 都存在）

```
→ 输出：「检测到项目代码库分析数据，将用于自动填充技术方案。」
→ 读取 _aggregated.json，进入阶段 B
```

**情况 2：部分数据存在**（`_todo.txt` 不为空，分析未完成）

```
→ 输出：「检测到代码库分析尚未完成（已处理 X/Y 个文件）。」
→ 询问用户：
   A. 先完成代码库分析（调用 /codebase-analyzer 继续）
   B. 使用已有的部分数据继续 PRD 拆分
   C. 跳过技术方案填充
```

**情况 3：无数据**（`.ai-docs/` 不存在或为空）

```
→ 输出：「未检测到代码库分析数据。代码库分析可以让技术方案部分自动填充推荐组件和参考代码。」
→ 询问用户（三选一）：
   A. 先运行代码库全量分析（调用 /codebase-analyzer，完成后自动继续 PRD 拆分）
   B. 提供现有的技术文档（DEV-GUIDE.md 或类似文件路径）
   C. 跳过，技术方案留空（保持 /prd-splitter 原有行为）
```

### 步骤 A.3：处理用户选择

**选择 A — 运行代码库分析**：

1. 确认项目根目录路径
2. 调用 `/codebase-analyzer` 完整流程
3. 分析完成后，读取 `.ai-docs/_aggregated.json`
4. 自动继续阶段 B

**选择 B — 用户提供文档**：

1. 获取用户提供的文件路径
2. 读取文件内容，提取技术栈、组件、模式等信息
3. 构建简化版技术参考数据（不需要完整的 _aggregated.json 格式）
4. 继续阶段 B

**选择 C — 跳过**：

1. 标记 `techMode = "skip"`
2. 直接进入阶段 B，技术方案部分使用原始模板（待开发补充）

## 阶段 B：PRD 内容提取

> 完整继承 `/prd-splitter` 的 PDF 处理能力。

### 步骤 B.1：确认输入与目标

1. **获取文档路径**：用户提供的 PRD 文档路径
2. **了解背景**（可选但推荐）：
   - 这个需求的业务背景是什么？
   - 涉及哪些角色（前端/后端/全栈）？
   - 有没有特别关注的模块？
3. **确认输出路径**：默认 `PRD拆分-{文档名}-{YYYYMMDD}/`

### 步骤 B.2：PDF 内容提取

> 本技能集成了 pdf skill 和 zai-mcp-server MCP，提供精准的文本、表格和图片提取能力。

#### 标准 PDF 处理

```python
import pdfplumber

with pdfplumber.open("PRD文档.pdf") as pdf:
    for i, page in enumerate(pdf.pages):
        text = page.extract_text()
        tables = page.extract_tables()
```

#### 表格提取（字段规格表是关键）

```python
import pdfplumber
import pandas as pd

with pdfplumber.open("PRD文档.pdf") as pdf:
    for page in pdf.pages:
        tables = page.extract_tables()
        for table in tables:
            if table and len(table) > 1:
                df = pd.DataFrame(table[1:], columns=table[0])
                print(df.to_markdown(index=False))
```

#### 扫描版 PDF / 图片处理

**必须使用 zai-mcp-server 进行二次校验，确保内容准确。**

```
工具: mcp__zai-mcp-server__extract_text_from_screenshot
参数:
  image_source: "page-01.png"
  prompt: "精确提取这个PRD文档页面中的所有文本内容，包括标题、正文、表格内容。保持原有的层级结构。"
```

> OCR 结果与 zai-mcp-server 结果有差异时，**以 zai-mcp-server 结果为准**。

#### 图片提取

```bash
# 提取所有嵌入图片
pdfimages -png "{PRD文件路径}" "assets/img"

# 获取图片页码映射
pdfimages -list "{PRD文件路径}"
```

## 阶段 C：需求理解与任务拆分

### 拆分原则

**每个拆分出的任务应该满足以下条件**：

| 维度     | 标准                         |
| -------- | ---------------------------- |
| 可执行性 | 一个开发人员可以独立完成     |
| 时间范围 | 预计 0.5-3 天可完成          |
| 独立性   | 可单独进行技术设计和代码评审 |
| 可测试性 | 有明确的验收标准             |

### 拆分层级

```
PRD 文档
  └── 模块 (如：订单管理)
        └── 功能 (如：订单列表)
              └── 任务 ⭐ (如：订单搜索筛选)  ← 这是我们要输出的颗粒度
                    └── 子任务 (如：日期范围选择器)
```

**重要**：如果一个"任务"预计超过 3 天，应继续拆分为更小的子任务。

### 什么算一个独立任务？

**好的任务拆分示例**：
- 订单列表 - 搜索筛选功能
- 订单详情 - 危险品信息导入按钮
- 用户管理 - 批量导入用户功能

**拆分过粗的示例**：
- 整个订单模块（太大，无法独立开发）
- 订单管理系统重构（范围不明确）

**拆分过细的示例**：
- 修改某个按钮的颜色（太小，不值得单独文档）
- 添加一个输入框（除非有复杂校验逻辑）

### 步骤 C.1：识别文档结构

- 版本迭代记录
- 模块划分（一级）
- 功能点（二级）
- 具体需求描述（三级及以下）

### 步骤 C.2：识别可执行任务

从 PRD 中识别出可独立开发的任务单元，每个任务应包含：

| 要素     | 说明                         |
| -------- | ---------------------------- |
| 功能描述 | 这个任务要实现什么功能       |
| 用户场景 | 用户在什么情况下使用         |
| 输入输出 | 功能的输入是什么，输出是什么 |
| 业务规则 | 有哪些业务逻辑和约束         |
| 交互说明 | 用户如何与功能交互           |
| 异常处理 | 异常情况如何处理             |

### 步骤 C.3：任务场景分类（用于匹配技术方案）

对每个识别出的任务，标注其**场景类型**，以便与代码库分析数据匹配：

| 场景类型 | 说明 | 对应 _aggregated.json 的 scenario |
|----------|------|----------------------------------|
| list | 列表页（含搜索、筛选、分页） | list |
| form | 表单页（新增/编辑） | form |
| detail | 详情页 | detail |
| modal | 弹窗操作 | modal |
| drawer | 抽屉操作 | drawer |
| import | 导入功能 | import |
| export | 导出功能 | export |
| chart | 图表/数据可视化 | chart |
| workflow | 流程/审批 | workflow |
| other | 其他 | other |

**每个任务生成一个独立的 Markdown 文件，内容越详细越好。**

根据阶段 A 的结果，技术方案部分有两种模式：

| 模式 | 条件 | 第 10 节内容 |
|------|------|-------------|
| **自动填充模式** | `_aggregated.json` 存在 | 基于代码库数据自动推荐组件、Hook、参考代码 |
| **留空模式** | 无代码库数据 | 使用原始模板，标注「待开发补充」 |

## 技术方案自动填充规则

### 数据源

所有技术方案内容**必须**来自以下数据文件，**严禁编造**：

| 数据源 | 用途 |
|--------|------|
| `.ai-docs/_aggregated.json` → `scenarios` | 匹配同类场景的文件列表 |
| `.ai-docs/_aggregated.json` → `componentIndex` | 推荐组件及真实使用代码 |
| `.ai-docs/_aggregated.json` → `hookIndex` | 推荐 Hook 及使用方式 |
| `.ai-docs/_aggregated.json` → `utilIndex` | 推荐工具函数 |
| `.ai-docs/COMPONENT-SELECTOR.md` | 按场景分类的组件选择参考 |
| `.ai-docs/components/*.md` | 每个组件的详细文档和所有使用示例 |
| `.ai-docs/hooks/*.md` | 每个 Hook 的详细文档 |
| `.ai-docs/scenarios/*.md` | 场景级别的开发模式参考 |

### 匹配算法

对于每个 PRD 任务，按以下步骤匹配技术方案：

**第一步：场景匹配**

```
任务的场景类型 → _aggregated.json.scenarios[场景类型]
→ 获取该场景下的所有文件列表
→ 获取该场景常用的 components 和 hooks
```

**第二步：组件推荐**

```
1. 从场景匹配结果中，取该场景下使用频率最高的组件
2. 根据 PRD 描述的 UI 元素，匹配对应组件类型：
   - PRD 提到"表格/列表" → 推荐 Table 类组件
   - PRD 提到"表单/输入" → 推荐 Form 类组件
   - PRD 提到"弹窗/对话框" → 推荐 Modal/Drawer 类组件
   - PRD 提到"搜索/筛选" → 推荐 SearchForm 类组件
   - PRD 提到"导入/上传" → 推荐 Upload 类组件
   - PRD 提到"导出/下载" → 推荐 Export 相关工具函数
   - PRD 提到"富文本/编辑器" → 推荐 Editor 类组件
3. 从 componentIndex 中取出推荐组件的使用示例代码
```

**第三步：Hook 推荐**

```
1. 取场景常用的 Hook
2. 根据任务需要的数据操作：
   - 需要请求接口 → useRequest
   - 需要表格+分页 → useAntdTable 或类似
   - 需要表单状态 → Form.useForm 或类似
3. 从 hookIndex 中取出使用示例
```

**第四步：参考文件推荐**

```
1. 从同场景的文件列表中，选择 2-3 个最相关的文件
2. 相关性判断依据：
   - 文件名/路径与 PRD 任务的功能相似
   - 使用的组件组合与 PRD 需求匹配
3. 列出文件路径，供开发参考
```

## 核心原则

### 必须做到

1. **忠实提取**：需求部分（1-9 节）只提取 PRD 中明确描述的内容
2. **详细完整**：每个任务文档应包含开发所需的全部业务信息
3. **独立自包含**：每个任务文档可独立理解
4. **嵌入原型图**：UI 相关的任务必须包含原型截图
5. **标注待定项**：不确定的内容标注「待确认」
6. **数据驱动**：技术方案部分（第 10 节）100% 基于代码库分析数据，不编造

### 绝对禁止

1. **不要编造需求**：不要生成 PRD 中没有的功能描述
2. **不要编造技术方案**：没有代码库数据时不要凭空推荐组件
3. **不要编造代码**：技术方案中的示例代码必须来自 `_aggregated.json`
4. **不要猜测**：不确定的内容要明确标注
5. **不要混淆来源**：明确标注哪些内容来自 PRD，哪些来自代码库分析

| 任务     | 推荐工具                | 说明                    |

### zai-mcp-server 工具

| 场景     | 工具                           | 用途                       |
| -------- | ------------------------------ | -------------------------- |

## 故障排除

### PDF 文本提取为空或乱码

**解决方案**：使用 zai-mcp-server 进行 AI 视觉识别

```
工具: mcp__zai-mcp-server__extract_text_from_screenshot
参数:
  image_source: "page-1.png"
  prompt: "精确提取图片中的所有中英文文本，保持原有格式和层级结构"
```

### 表格结构识别错误

**解决方案**：使用 zai-mcp-server 的 analyze_image 进行视觉分析

```
工具: mcp__zai-mcp-server__analyze_image
参数:
  image_source: "page-with-table.png"
  prompt: "识别表格结构，提取所有列标题和数据，输出为 Markdown 表格格式"
```

### 代码库分析数据与 PRD 场景不匹配

如果 PRD 中的功能场景在代码库中没有类似实现：

1. 技术方案中标注「项目中无同类场景，以下为通用建议」
2. 仅推荐基础组件（antd 等），不推荐业务组件
3. 不提供参考代码（因为没有真实来源）
4. 建议开发人员参考外部文档
